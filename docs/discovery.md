# Discovery: data contract and sign-off

This is a template for agreeing a file drop with the party who sends it. The
worked example below is a fictional scenario with generated data. The company,
the people and the figures do not exist. No real customer data is in this
repository.

## 3. Worked example (fictional)

Scenario: a fictional online shop named "Example Parts Ltd" sends one order
file per day. The file contains new orders and status changes. The shop
sends a corrected file when an order was mistyped. The company, the people
and the numbers are invented for this example.

### 3.1 Filled template

| field | value |
|---|---|
| Drop name | `orders.csv` |
| Sender | fictional shop's order export job |
| Format and encoding | csv, UTF-8, header row required |
| Delivery | one file per day, into the drop folder |
| Natural key | `order_id` |
| Columns | `order_id` text required; `customer_id` text required; `sku` text required; `quantity` int required, 1 to 1000; `unit_price_cents` int required, 0 to 1000000; `order_date` date required; `status` text required, one of placed, shipped, cancelled |
| Exact header match | yes |
| Expected rows per drop | 50 to 5000 |
| Rejected row decided by | the shop's operations contact |
| Changed row decided by | the shop's operations contact, then an engineer re-runs with a new drop |
| Reconciliation totals | the shop compares its own row count with the manifest row count |
| Raw drop retention | kept for 90 days |

### 3.2 Generated data

The three drops in `fixtures/e2e/` are generated by hand for the tests, and the
drill data is generated by `scripts/gen_drill.py` with a fixed seed. Neither is
real data. The `fixtures/e2e` drops are small and are kept in the repository.
The drill data is written under `build/` and is not committed.

### 3.3 What the worked example shows

- Day 1 is the first drop. Its rows are applied, except the rows that break a
  rule.
- Day 2 is a revision of the same file name. Unchanged orders are duplicates,
  new orders are applied, and an order whose quantity was corrected is
  rejected with `changed_since_applied`. The operations contact has to decide
  what to do with that row.
- Day 3 is a byte-identical resend of day 2. It is a no-op at the manifest.

### 3.4 Questions to ask a sender whose totals differ

1. Which file name and which file hash did you send? (The report prints both.)
2. How many rows did your export contain, and does that include the header?
3. Which reason codes in the report do your missing rows match?
4. Did the export change between the two sends? If yes, send the new file as a
   revision and say which orders changed.
